# RYVEN 3.0 — Milestone 17.10 Phase 5: Model Intelligence Telemetry, Performance Governance & Operational Observability

## Architecture Overview

Phase 5 introduces a centralized, privacy-preserving, thread-safe telemetry and operational performance governance service (`ModelTelemetryService`) for RYVEN 3.0's multi-provider AI subsystem. The service instruments request life cycles across `ModelRouter`, `UnifiedAIProvider`, provider adapters, and `ModelSecurityGateway` while enforcing strict privacy invariants and fail-closed security guarantees.

```
AIRequest / Consumer
       │
       ▼
ModelRouter (Logical Request ID assigned / tracked)
       ├── Telemetry: REQUEST_ACCEPTED
       │
       ▼
ModelSecurityGateway (Authoritative Policy Check)
       ├── Telemetry: SECURITY_EVALUATION / ALLOWED / DENIED / REDACTED
       │     (Denials remain fail-closed regardless of telemetry health)
       │
       ▼
Primary Provider Attempt (Ollama Local / Grok Remote / HF)
       ├── Telemetry: PROVIDER_REQUEST_STARTED
       ├── Streaming: STREAM_FIRST_TOKEN (TTFT monotonic latency)
       ├── Telemetry: PROVIDER_REQUEST_COMPLETED / FAILED / TIMEOUT
       │
       ▼ (On Failure & Eligible Fallback)
Fallback Provider Attempt (Fallback Depth = 1)
       ├── Telemetry: FALLBACK_ATTEMPTED / SUCCEEDED / FAILED
       ├── Telemetry: PROVIDER_REQUEST_STARTED / COMPLETED
       │
       ▼
Completion / Finalization
       └── Telemetry: REQUEST_COMPLETED / REJECTED (Overall Duration)
```

## Privacy & Zero-Store Telemetry Guarantees

Telemetry strictly adheres to a zero-store policy for sensitive data:

1. **Strictly Forbidden Fields (Never Persisted)**:
   - Raw user prompts, system prompts, or multi-turn conversational history.
   - Model responses, generated chunks, or stream output.
   - API keys, bearer tokens, passwords, cookies, or confirmation tokens.
   - Raw exceptions, stack traces containing request bodies, or unsanitized payloads.
   - Auth headers or credentials.

2. **Recursive Allowlisting & Sanitization**:
   - Only allowlisted metadata keys are retained (`provider`, `model_id`, `task_type`, `complexity_tier`, `is_remote`, `privacy_mode`, `status`, `error_type`, `error_category`, `fallback_attempted`, `fallback_provider`, `fallback_reason`, `first_token_latency_ms`, `total_duration_ms`, `input_tokens`, `output_tokens`, `total_tokens`, `estimated_cost`, `currency`, `circuit_state`, `reason`).
   - Deep nested dictionaries and lists are sanitized recursively; any value containing known secret markers (`sk-`, `ghp_`, `AKIA`, `Bearer`, `password=`, etc.) is redacted with `[REDACTED]`.
   - Error messages are normalized into safe error categories (`timeout`, `unavailable`, `rate_limit`, `authentication`, `security_denial`, `invalid_request`, `internal_error`).

3. **Fail-Closed Security Invariant**:
   - A telemetry failure (e.g., buffer exhaustion, emission exception) never alters or weakens `ModelSecurityGateway`.
   - Security denials remain strictly fail-closed.
   - Action bus audit events are published reliably.

## Logical Request vs. Provider Attempt Accounting

To eliminate double-counting during retries or fallbacks:
- **Logical Request (`AIRequest`)**: Represents the end-to-end task initiated by the caller, tracked under a single correlation `request_id`. Records accept/reject, overall duration, final outcome, and whether fallback was invoked.
- **Provider Attempt**: Represents a discrete attempt against an individual provider/model (primary or fallback). Each attempt tracks its own start/completion timestamps, duration, status, and provider-specific error category.
- **Fallback Accounting**: Fallbacks are explicitly tracked as distinct attempts under the parent `request_id`. The fallback rate is calculated as `fallback_requests / total_completed_requests`, preventing skew from multiple attempts within a single request.

## Performance Governance & Latency Summaries

1. **Bounded Ring Buffers**:
   - Thread-safe deque structures protected by `threading.RLock`.
   - Bounded event history (default: 2,000 events) and request history (default: 1,000 requests) to strictly guard memory utilization.
2. **Deterministic Latency Percentiles**:
   - Calculates sample count, average, median (P50), P95, and P99 latencies using sorted nearest-rank interpolation.
   - First-token latency (TTFT) is measured using monotonic clocks (`time.perf_counter()`) for streaming requests.
3. **Usage & Cost Governance**:
   - Token counts are recorded only when genuinely supplied by trusted provider metadata.
   - When token metadata is absent or unsupported, token usage remains `None` (JSON `null`), never fabricated or assumed as zero.
   - Estimated cost is computed strictly when explicit pricing rules are configured; otherwise, it remains `None` (`null`).

## Operational APIs & Endpoints

Authenticated, read-only operational observability endpoints:
- `GET /v1/models/telemetry`: Returns aggregated telemetry summaries, including total requests, active requests, provider-specific metrics (success/failure/timeout counts, latency percentiles, TTFT percentiles), local vs. remote distribution, fallback counts, and retention stats.
- `GET /v1/models/telemetry/events?limit=N&event_type=...`: Returns the recent bounded event log with allowlisted, sanitized metadata. Raw prompts, model outputs, and credentials are never returned.

## RAVAN Dashboard Integration

The developer `ModelStatusPanel` in the RAVAN frontend provides a dedicated **Operational Observability & Performance Governance** card featuring:
- Total requests and active requests count.
- Local vs. Remote inference breakdown.
- Circuit breaker state indicators.
- Fallback rate percentage.
- Primary provider latency summaries (P50 and P95).
- Streaming First-Token Latency (TTFT P50 and P95).
- Memory-bounded buffer utilization metrics.
- Active Zero-Store Privacy Policy compliance badge.
